Date: 2026-09-24. Offline measurement only; nothing lifted or booted yet.

## Notable differences from GoW2

- **cellSail (40 imports, 0 wired):** the Sail movie player. GoW2 plays video
  through cellVdec directly; this game uses the high-level player. Largest gap.
- **SPURS job chains** (`cellSpursCreateJobChainWithAttribute`, event-flag
  LV2 queue detach): not used by GoW2.
- **sys heap** (`_sys_heap_create_heap/malloc/memalign/free`) and
  `sys_prx_register_library`, `sys_spu_image_close`: missing in sysPrxForUser.
- NP/network imports (sceNp, sceNp2, NetCtl, Commerce2): likely stub-able
  (offline play).
- Multi-platform licensed title (also on 360/Wii U): expect lighter, more
  generic SPU usage than a first-party Cell-native engine. Not yet verified.

## Frame loop running (same day, later)

The main thread's first wall was NOT the job chain (hypothesis above was
wrong in its first form). Chain of measured causes, each confirmed against the
RPCS3 oracle (`tools/oracle_gpu_sample.py`, headless, interpreter decoders,
per-title Null pad config -- see "Oracle" below):

1. Frame loop `func_000F7CF4` waits `ctrl->ref == parity` unless ref == -1.
   Console starts ref at 0xFFFFFFFF; we started at 0 and bumped it on every
   GetControlRegister. Fix: ref=-1 init, `PS3_GCM_REF_BUMP=0`.
2. Then `cellSpursEventFlagWait`: the flag at 0x00A96780 is set by the chain's
   job (0x0084E500, JOBCRT Ver14) with atomics on the firmware layout; our HLE
   stored host-endian fields over `events`. Fix: firmware layout + atomics.
3. Job chain: JTS-prefilled command list, GUARD at 0x00A96800. Implemented
   (walker + jobs in the SPU interpreter).
4. Chain entry rewritten to `NEXT 0` on the 2nd lap: wrong r25 after the frame
   limiter -- lifter treated `lv2_syscall` as a terminator, so fragment
   func_000F8038 returned without the epilogue (stack leak 0xE0/frame).

Result (45 s headless, `./run_ben10.sh`): 136 flips, 142 jobs, 0 SPU halts,
10 files opened, reaches the first intro movie `Movies/CNi_logo.pam`.

## libsail via firmware LLE (same day, later)

cellSail is run as the REAL firmware module instead of an HLE: the user's
`dev_flash/sys/external/libsail.sprx` (RPCS3 install) is decrypted with our
`ps3_unself` (APP type, key rev 0x1C), relocated to 0x28000000 by
`ps3recomp/tools/lift_prx.py`, lifted with `--raw --base --symbol-prefix sail_`
(587 functions, 0 fallback stubs) and bound by `gen_prx_bind.py`. Everything
under `firmware/` and `recomp_prx_sail/` is firmware-derived and gitignored;
`build_macos.sh` links it only when present (weak `g_lle_sail`).

Recipe (from this directory):
```bash
F=~/Library/Application\ Support/rpcs3/dev_flash/sys/external/libsail.sprx
ps3_unself "$F" firmware/libsail/libsail.prx
python3 ../ps3recomp/tools/lift_prx.py firmware/libsail/libsail.prx --base 0x28000000 -o firmware/libsail
python3 ../ps3recomp/tools/ppu_lifter.py firmware/libsail/libsail_image.bin --raw --base 0x28000000 \
    --functions firmware/libsail/libsail_functions.json --code-end 0x280259d0 --symbol-prefix sail_ \
    -o recomp_prx_sail -j 8
python3 ../ps3recomp/tools/gen_prx_bind.py --dir firmware/libsail --name libsail --prefix sail_ \
    --lift-dir recomp_prx_sail --sysmodule 0x001D --out firmware/libsail/libsail_bind.cpp
```

Engine walls cleared on the way (ps3recomp 688d34ec, 1388afda, 1162d26d, bde7c909):
LLE runtime support; ICALL-HEAP breaker skipped the registered libsail code;
SPU syscall block mis-numbered since v0.1.0 (182 = read_ls, not set_argument);
giant lock held across sys_cond_wait / contended sys_mutex_lock /
sys_ppu_thread_join (deadlocks); `_sys_mem*`/`_sys_str*`/`_sys_printf` on host
pointers; `_sys_heap_*` missing (libsail got heap 0 and the game's own heap got
corrupted during map load); cellPadPeriphGetInfo / cellAudioOutGetState and 4
others unresolved (returned OK with untouched out-structs).

State (headless, 40-90 s): all intro movies were being skipped while libsail had
no heap (game reached the first map load); with a real heap libsail now goes
further and the game stays in `cellSailPlayerCreateDescriptor` for the first
movie (`CNi_logo.pam`): the main thread waits on libsail's control thread,
which has already exited. libsail made no Pamf/Dmux/Vdec/Adec call yet -- it
drives the game's own registered source (guest callbacks). Next: why
`_libsail-control` returns (its syscalls under PS3_TRACE_THREADS=1).

## Past CreateDescriptor: jump tables, signal_to, thread ids, libpamf LLE (same day, evening)

Four more engine walls, each measured with the gated per-thread syscall trace
(`PS3_TRACE_SC_THREAD=<name substring>`, e.g. `libsail` or `main`):

1. **Jump tables the lifter missed** (`[ICALL-HEAP] skip ctr=0x28013980`): libsail's
   control loop (`sail_func_280126E8`) keeps its 213-entry table base in a stack slot
   (`std r7,0x370(r1)` ... `ld r10,0x370(r1); lwzx`), dispatches through 77 one-word
   TOC gotos (`lwz r0,d(r2); mtctr; bctr`), and a `cmpwi cr4,r3,0` on a syscall result
   was read as the switch bound (count 0). `discover_jump_tables` now follows the spill,
   turns TOC gotos into one-case tables (kept only inside the enclosing function) and
   ignores a 0 bound: 18 -> 97 dispatchers here; GoW2 unchanged (157 / 1788).
   Raw lifts also take `--toc` now.
2. **`sys_cond_signal_to` (syscall 110) missing**: the control thread answers the
   caller of `cellSailPlayerCreateDescriptor` with `signal_to(cond, caller_id)`; the
   stub returned OK and woke nobody. sys_cond now keeps a FIFO of waiters.
3. **Thread ids**: HLE `sys_ppu_thread_get_id` returned 1 on every thread, and created
   threads were numbered from 1 too. Now the primary thread is id 1 (slot 0, with its
   priority from the ELF's PT_PROC_PARAM, 1010 here) and created threads start at 2.
   Without the slot, `sys_ppu_thread_get_priority(1)` returned ESRCH and the game
   aborted SPURS init and exited.
4. **libpamf** runs as LLE too (base 0x28100000, no module_start). The game never loads
   it itself: an LLE module now starts the LLE modules it imports from first.
   Also: cellSysmodule's id table was shifted by a made-up SYNC2 at 0x0E -- 0x12 is
   PAMF (the game loads 0x12 + 0x1D before each movie), 0x25 VdecAvc, 0x28 AdecAtx,
   0x2A DmuxPamf. Names only.

Recipe for libpamf (same as libsail, `--code-end` = base + filesz of the text segment):

`libapostsrc_mini` needs its decrypted file and dir renamed to the `libapostsrc` stem
(`firmware/libapostsrc/libapostsrc.prx`) because `build_macos.sh`'s `LLE_MODULES` loop
maps the short name `apostsrc` to `firmware/lib$m`.

**libavcdec and libapostsrc_mini do not lift**: `ppu_lifter.py` aborts in
`discover_jump_tables` with `UnboundLocalError: local variable '_lwz_of' referenced
before assignment` (`tools/ppu_lifter.py:3910`, inside the "computed goto through one
TOC word" branch added for the E162 jump-table fix). Root cause (read, not patched --
out of scope for this task): `_lwz_of` is a nested `def` at line 3951, later in the
*same* `for` loop body; Python decides a name is local to the whole enclosing function
at compile time from every `def`/assignment anywhere in it, regardless of source
order, so the reference at line 3910 is local too -- if the very first `bctr` this call
seeds (no `lwzx` before it, i.e. a TOC-goto pattern) is hit before any earlier
iteration has gone through the branch that runs the `def`, it's unbound. Both modules
apparently hit a TOC-goto as their first unresolved `bctr`. libsail (the module the
E162 fix targeted) never hits this because its `sail_func_280126E8` dispatcher's
`lwzx`-based table appears earlier in scan order. Not re-attempted with
`--allow-jt-failure` (degrades the switches involved, not requested by this task).
These two modules stay HLE; not registered in `boot_macos.cpp`.

**Build fix (`boot_macos.cpp` + `build_macos.sh`, this task's files):** the existing
sail/pamf pattern (`extern ... __attribute__((weak)); if (&g_lle_x) ppu_lle_add(...)`)
does not actually degrade gracefully when a module's bind unit is absent from the
link -- measured with libavcdec/libapostsrc missing: `ld` fails with "Undefined
symbols for architecture arm64" for `_g_lle_avcdec`/`_g_lle_apostsrc`. On Darwin, in a
statically linked executable, a `weak` *declaration* with no definition anywhere in
that link is a hard link error, not a null pointer at runtime -- the "resolves to 0 if
absent" idiom is a dyld (separate dylib/framework) feature and never applied here; this
matches the same finding already on record for the PGO writer's weak declaration
(`ppu_loader.cpp`, "nem `weak` nem `weak_import` fazem o simbolo ficar nulo"). Fixed by
moving "is this module present" to compile time: `build_macos.sh` step 3b now also
emits `-DPS3_LLE_HAVE_<M>=1` per module actually linked (same presence check it
already does for the `.o` files), passed to the `boot_macos.o` compile in step 4;
`boot_macos.cpp` gates each `extern ... g_lle_<m>` declaration and its
`ppu_lle_add(&g_lle_<m>)` call with `#ifdef PS3_LLE_HAVE_<M>` instead of `if (&g_lle_x)`.
Applied uniformly to all 8 new modules and to sail/pamf (previously untested with
their firmware truly absent, since both have always been present in every build so
far). `LLE_MODULES` default now: `sail pamf dmux dmuxpamf adec atxdec vdec avcdec
vpost apostsrc` (`avcdec`/`apostsrc` fall back to HLE automatically once their
`firmware/lib<m>/` is absent -- no source change needed if the lifter bug above ever
gets fixed and they start lifting cleanly).

**VM range check (Step 1):** 50 s headless with `PS3_TRACE_ALLOC=1`, no game code

## Round 2: libavcdec and libapostsrc_mini unblocked (same day)

helpers above the loop that calls them, fixing the `UnboundLocalError` above. Both

above (avcdec sysmodule 0x0025, apostsrc sysmodule 0). No source change needed in
`boot_macos.cpp`/`build_macos.sh`: the `-DPS3_LLE_HAVE_<M>` gating added in Round 1
already covers a module that starts existing.

Build: all 10 modules now LLE (`libavcdec: LLE (24 objects)`, `libapostsrc: LLE (6
objects)`). 50 s headless run, same recipe: both `module_start` return `0x0`, no
crash; `libvdec_Library` now resolves 10 imports directly against libavcdec's exports
(`121 imports -> HLE, 10 -> LLE, 0 vars`, was `131 -> HLE, 0 -> LLE`) and
`cellSail_Library` picks up 5 more LLE-resolved imports (`34 -> HLE, 56 -> LLE`, was

Task/Taskset API, Task 3 territory), no new ones; no regression.
